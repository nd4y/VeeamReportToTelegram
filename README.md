# VeeamReportToTelegram

PowerShell-скрипт для отправки отчётов о состоянии заданий бекапа Veeam Backup & Replication в Telegram.

Скрипт собирает статус всех заданий, посчитывает RPO (время с момента последней точки восстановления), формирует сводку и отправляет её сообщением в указанный Telegram-чат через бота.

## Пример отчёта

![Пример отчёта в Telegram](example.png)

Для каждого задания в отчёт попадают:
- **Name** — имя задания
- **Job Type** — тип задания
- **Job status** — текущий статус (Working / Stopped / ...)
- **RPO** — время с момента последней точки восстановления, часы (со значком по цвету, см. ниже)
- **Last result** — результат последнего запуска (Success / Warning / Failed / None, со значком по цвету)
- **Latest restore point** — дата и время последней точки восстановления
- **Total backup size** — суммарный размер бекапов задания

Цветовые пороги для RPO и статуса заданы в скрипте и могут переопределяться индивидуально для конкретных заданий (см. [Кастомные пороги RPO](#кастомные-пороги-rpo)).

## Поддерживаемые типы заданий

В отчёт попадают все задания, которые возвращает `Get-VBRJob`, независимо от типа — специальной обработки требует только способ добраться до точек восстановления:

- обычные задания (VMware, Hyper-V, Backup Copy, агентские и прочие) — бекап ищется в `Get-VBRBackup` по `JobId`, точки берутся через `Get-VBRRestorePoint`
- задания по неструктурированным данным (File Backup, NAS Backup Copy) — бекап ищется в `Get-VBRUnstructuredBackup` (в старых версиях `Get-VBRNASBackup`), точки — через `Get-VBRUnstructuredBackupRestorePoint`

### Откуда берётся дата последней точки восстановления

Дата считается **по самим точкам восстановления** (максимальный `CreationTime`), а не по метаданным задания. Это принципиально: метаданные врут.

- `LastPointCreationTime` у большинства заданий пустой — задание с живыми бекапами выглядело как `No restore points` и получало RPO `9999h`
- `MetaUpdateTime` у Backup Copy в объектное хранилище остаётся на дате создания задания — при ежедневно работающих копиях отчёт показывал RPO в тысячи часов

Если точки получить не удалось, используются фолбеки в порядке убывания достоверности: `LastRestorePointCreationTime` / `LastPointCreationTime` бекапа, затем время завершения последней сессии задания. Если не сработало ничего — в отчёте `No restore points` и RPO `9999h`.

### Бекапы без задания

Бекапы, которым не соответствует ни одно задание (например, агентские, управляемые со стороны агента), выводятся отдельными строками со статусом `No job`. Без этого бекап, не обновлявшийся месяцами, просто отсутствовал в отчёте — вместе со своим RPO. Отключается параметром `IncludeBackupsWithoutJob=false` в конфиге.

### Размер бекапа

Размер считается по `GetAllChildrenStorages()` с фолбеком на `GetAllStorages()`: последний возвращает `0` почти для всех бекапов, в том числе для всех, лежащих в объектном хранилище.

У NAS-бекапов (`VBRNASBackup`) нет ни storages, ни свойств размера, поэтому размер берётся из последней сессии задания — из `BackupTotalSize`. Не из `Progress.TotalUsedSize`: он равен `ProcessedSize`, то есть объёму, обработанному за конкретный запуск, и на инкрементальном запуске занижает размер в разы.

Если размер получить не удалось, в отчёте будет `Unknown`.

## Требования

- Veeam Backup & Replication (скрипт использует командлеты модуля `Veeam.Backup.PowerShell`, который устанавливается вместе с VBR/консолью)
- PowerShell, запускаемый на сервере VBR (или на машине с установленной консолью VBR и правами на подключение к серверу)
- Telegram-бот и chat ID чата/канала, куда будут приходить отчёты

## Установка

1. Скопируйте `VeeamReport.ps1` и `VeeamReport.conf` на сервер, например в `C:\scripts\`.
2. Заполните `VeeamReport.conf` (см. ниже).
3. Запустите скрипт вручную, чтобы убедиться, что отчёт приходит в Telegram:
   ```powershell
   C:\scripts\VeeamReport.ps1
   ```
4. Настройте запуск по расписанию через Планировщик заданий Windows (Task Scheduler), например раз в сутки.

## Настройка (VeeamReport.conf)

```ini
TelegramBotToken=<токен вашего бота>
TelegramChatId=<ID чата или канала>
#CustomRPOMap=[{"JobName":"Custom Backup","RPOMap":{"168":"Green","336":"Yellow"}}]
#IncludeBackupsWithoutJob=true
```

- `TelegramBotToken` — токен бота, полученный от [@BotFather](https://t.me/BotFather).
- `TelegramChatId` — ID чата/группы/канала, куда бот должен отправлять сообщения (бот должен быть добавлен в чат и иметь права на отправку сообщений).
- `CustomRPOMap` — необязательный параметр (см. [Кастомные пороги RPO](#кастомные-пороги-rpo)).
- `IncludeBackupsWithoutJob` — выводить ли бекапы, которым не соответствует ни одно задание (см. [Бекапы без задания](#бекапы-без-задания)). По умолчанию `true`.

По умолчанию скрипт ищет файл конфигурации по пути `C:\scripts\VeeamReport.conf`. Путь можно переопределить параметром при запуске:

```powershell
C:\scripts\VeeamReport.ps1 -ConfigPath "D:\Veeam\VeeamReport.conf"
```

## Кастомные пороги RPO

По умолчанию для всех заданий используется порог: RPO ≤ 24ч — зелёный, ≤ 48ч — жёлтый, больше — красный.

Для отдельных заданий (например, редко запускаемых архивных копий) можно задать собственные пороги JSON-строкой `CustomRPOMap` в `VeeamReport.conf`:

```
CustomRPOMap=[{"JobName":"Custom Backup","RPOMap":{"168":"Green","336":"Yellow"}},{"JobName":"Custom 2 Backup","RPOMap":{"9998":"Green","9999":"Yellow"}}]
```

`JobName` должен точно совпадать с именем задания в Veeam. Параметр не обязателен — если он не задан, для всех заданий используются пороги по умолчанию. Порядок порогов в JSON не важен — они сортируются по числовому значению.

## Отправка и обработка ошибок

- Текст отправляется POST-запросом с JSON-телом, спецсимволы (`<`, `>`, `&`) в именах заданий экранируются — сообщение не ломается от «неудачных» имён.
- Отчёт длиннее лимита Telegram (4096 символов) автоматически разбивается на несколько сообщений с пометкой `(part 1/N)`.
- При сбое отправки выполняется до 3 попыток; если Telegram вернул флуд-лимит (`retry_after`), пауза перед повтором увеличивается до запрошенной.
- Если данные из Veeam получить не удалось, в Telegram уходит сообщение с текстом ошибки — скрипт мониторинга не умирает молча.
- При неудачной отправке или сбое сбора данных скрипт завершается с кодом возврата `1` — в Планировщике заданий это видно как сбой (`Last Run Result`).
- Если размер бекапов задания посчитать не удалось, в отчёте будет `Unknown`.

## Известные ограничения

1. Бекап ищется по `JobId`, а если совпадения нет — по точному имени задания. У бекапа с именем, отличающимся от имени своего задания и с незаполненным `JobId`, размер и дата определены не будут (в отчёте `Unknown` / `No restore points`).
2. `Last result` берётся из `Info.LatestStatus` задания и отражает только последний запуск. Если задание сегодня падало несколько раз, а последняя попытка прошла успешно, в отчёте будет `Success`.
3. Для бекапов без задания результат последнего запуска неизвестен — в колонке `Last result` выводится `Unknown` с красным значком.
